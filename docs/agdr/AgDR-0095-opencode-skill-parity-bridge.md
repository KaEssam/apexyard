# opencode Skill-Parity Bridge — Generate `/command` Shims Over `.claude/skills`

> In the context of bringing opencode to full parity with Claude Code (the gate adapter in AgDR-0092 already closed the enforcement gap), facing the fact that apexyard's 64 `.claude/skills/*/SKILL.md` are surfaced as typed slash commands under Claude Code but not under opencode, I decided to ship a generator (`bin/install-opencode-commands.sh`) that writes one thin re-export shim per skill into `.opencode/commands/`, each embedding its SKILL.md via opencode's `@` file-reference and forwarding `$ARGUMENTS`, to achieve single-source-of-truth skill invocation across both harnesses without duplicating skill logic, accepting the residual gap that per-skill `subtask`/`agent` frontmatter tuning is left unset in v1 (deferred to a follow-up) and that the shims embed the SKILL.md raw — including Claude-Code-specific `allowed-tools:` frontmatter that is inert text under opencode.

## Context

AgDR-0092 shipped the opencode **gate** adapter (`bin/install-opencode-adapter.sh` + `harness-adapters/opencode/`), which bridges apexyard's mechanical gates (merge block, ticket-first, secrets scan, red-CI, AgDR) by shelling out to the unmodified `.claude/hooks/*.sh` on opencode's `tool.execute.before` event. That closed the **enforcement** gap between opencode and Claude Code.

The **invocation** gap remained. Under Claude Code, each `.claude/skills/<name>/SKILL.md` is auto-discovered and turned into a typed slash command — `/feature`, `/handover`, `/projects`, `/inbox`, `/code-review`, `/approve-merge`, ... — 64 of them. Under opencode, the adopter had to manually `Read` each `SKILL.md` and tell the model to follow its process. opencode's own commands feature (opencode docs: `docs/commands/`) loads markdown files from `.opencode/commands/<name>.md` (with YAML frontmatter `description:`, a template body, and `$ARGUMENTS` / `@<path>` placeholders) and exposes them as `/<name>` in the TUI. So opencode already has the mechanism apexyard needs; the framework just wasn't generating the shims.

The design precedent is the same "thin transport" shape the gate adapter (AgDR-0092) and the Codex adapter (AgDR-0088) already established for their respective concerns: keep the canonical artefact single-source (the SKILL.md stays the source of truth under `.claude/`), and generate only the harness-facing redirect. The Codex adapter generates `.agents/skills/` from `.claude/skills/`; this adapter generates `.opencode/commands/` from the same source.

Ticket: KaEssam/apexyard#3 ("opencode skill-parity: bridge .claude/skills as /commands shims").

## Options Considered

| Option | Pros | Cons |
|--------|------|------|
| **Hand-author 64 `.opencode/commands/*.md` files and commit them to the framework repo** | No generator to maintain; files are diffable as source | Pure duplication — every skill edit needs a parallel edit to the shim; guaranteed drift; the framework repo would carry 64 files that exist solely to redirect to neighbours already in the same repo |
| **Generate the shims from `.claude/skills/` and commit the generated output** | Same convergence property as the gate adapter's install script — adopters get shims by running a script, not by hand-copying | The generator is the source of truth either way; committing its output is redundant ceremony the gate adapter deliberately avoids (`.opencode/` is gitignored — see `.gitignore` line 72), and would create a second copy that drifts the moment a skill changes without a re-run |
| **Generate the shims at session-start via an opencode plugin (mirror the gate adapter's settings.json derivation)** | True zero-drift — shims regenerate on every session | opencode discovers `/commands` at startup from a directory, not from a plugin's runtime output; a plugin cannot inject commands into the TUI's `/<name>` menu in time for discovery. The gate adapter reads JSON at plugin-init because that's how opencode's hook API works — opencode's command API is filesystem-discovery, not plugin-injected |
| **Generate the shims via a script the adopter runs once, into gitignored local output (CHOSEN)** | Matches the established gate-adapter install shape (`bin/install-opencode-adapter.sh`); `.opencode/` already gitignored so no committed drift; the SKILL.md is the single source of truth; re-running is idempotent (overwrites); a skill update just needs a re-run | Adopters must remember to re-run after a `/update` pull that changes skills — same operational discipline the gate-adapter install already requires (and advertises in its "Next" footer) |

## Decision

Chosen: **ship `bin/install-opencode-commands.sh` — a sibling of `bin/install-opencode-adapter.sh` — that scans `.claude/skills/*/SKILL.md` and writes one `.opencode/commands/<name>.md` shim per skill into the project's local (gitignored) `.opencode/commands/`.** The shim body uses opencode's `@<path>` file-reference to embed the SKILL.md content into the prompt and `$ARGUMENTS` to forward parameters, so the SKILL.md stays the single source of truth — a skill update needs no shim edit, only a re-run of the script (which overwrites).

Three supporting decisions, made while building the generator:

- **`description:` is sourced from the SKILL.md YAML frontmatter, with the first `#` heading line as fallback.** The frontmatter `description:` field is the curated one-line summary each skill already maintains for Claude Code's own command menu; reusing it keeps a single description source. The fallback covers the handful of skills whose `SKILL.md` opens with a heading before any frontmatter, and produces a reasonable TUI label (`/feature — Create a Feature Request Ticket`) when frontmatter is absent. Both branches strip a trailing CR so the parser works under CRLF checkouts (Windows) as well as LF — a CRLF SKILL.md has `---\r` as its fence line, which a naive `case "---")` would never match, silently skipping the whole frontmatter (this was a live bug during this change, caught by reading the generated `feature.md` and fixed before commit).
- **No `subtask` or `agent` frontmatter is set in v1.** opencode's command frontmatter supports `subtask: true` to force a subagent so the command's work doesn't pollute the primary context, and `agent: <name>` to route to a specific agent. Heavy agentic skills (`/launch-check`, `/code-review`, `/c4`, `/threat-model`) would arguably benefit from `subtask: true`; light read-and-report skills (`/status`, `/projects`, `/inbox`) want the primary agent. Setting it per-skill by hand is a 64-row curation the first cut doesn't need; and the right default is not obvious without live use. v1 leaves both unset and lets opencode pick per its agent config — the documented follow-up is to revisit once adopters report context-pollution issues.
- **The shim embeds the SKILL.md raw, including its Claude-Code-specific frontmatter.** opencode's `@` reference includes the file content verbatim, so the SKILL.md's `---`-fenced `allowed-tools:`, `argument-hint:` etc. become inert text in the prompt. They are harmless (the model ignores fields it doesn't recognise) and the alternative — stripping the frontmatter at generation time — would mean the shim embeds a *different* document from the canonical SKILL.md, reintroducing the drift risk this adapter exists to eliminate. The cost is a few tokens of inert frontmatter per command invocation, accepted.

## Consequences

- opencode is now at parity with Claude Code for **both** layers: mechanical gates (AgDR-0092) and skill invocation (this AgDR). An adopter running `opencode run --auto` from a project with both adapters installed sees the same `/feature`, `/handover`, `/projects`, `/inbox`, `/code-review`, `/approve-merge` … menu Claude Code adopters see, and the same gates fire on tool calls.
- The generator is idempotent — re-running overwrites. After an `/update` pull that changes skills, an adopter re-runs `bash bin/install-opencode-commands.sh` to refresh the shims. This is the same operational discipline `bin/install-opencode-adapter.sh` already requires, and the two scripts' "Next" footers now cross-reference each other so an adopter installing one is told about the other.
- `.opencode/` is gitignored (`.gitignore` line 72), so the generated shims are local-per-adopter and never committed — consistent with the gate adapter's installed `.opencode/plugins/apexyard/`. The framework ship is the **generator**, not the generated output.
- Per-skill `subtask`/`agent` tuning is deferred. If adopters report that `/launch-check` or `/code-review` pollutes the primary context under opencode, the generator can grow a small per-skill override map (`heavy-agent-skills.txt` or similar) without changing any SKILL.md. This is the follow-up this AgDR names.
- The shims rely on opencode's `@` file-reference and `$ARGUMENTS` placeholder behaviour as documented (opencode docs/commands, live-verified install shape from AgDR-0092's #844 update). This build was not re-verified against a live, credentialed opencode model turn — the gate adapter's #816/#821 live proof covers the gate layer; this adapter's correctness rests on opencode's documented `@`-reference and `$ARGUMENTS` behaviour and was tested by generating 65 shims and inspecting a sample. A live `/feature` round-trip under `opencode run --auto` is the closing verification step once model credentials are available (same honest-gap posture as AgDR-0092's "one hop still resting on spike #816").

## Artifacts

- `bin/install-opencode-commands.sh` — the generator (scans `.claude/skills/*/SKILL.md`, writes `.opencode/commands/<name>.md` per skill, idempotent, CRLF-safe frontmatter parse)
- `docs/harnesses/opencode.md` — new "Skill parity" section documenting the install alongside the gate section
- `.opencode/commands/*.md` — generated output (gitignored, not committed)
